# docs 작업 지침

문서 전반과 글쓰기 규칙은 루트 AGENTS.md를 따른다. 여기에는 docs/ 안에서만 쓰는 규칙을 적는다.

## 구조

- `<단계>/`: 파이프라인 단계별 문서. 지금은 `parsing/`, `chunking/`이 있고, 다음 단계 작업을 시작할 때
  같은 형식으로 만든다.
  새 단계 폴더를 만들면 `.github/docs-check.json`의 짝 규칙(그 단계 코드·실행 결과 → 그 단계 문서)도 같은 커밋에서 추가한다.
  - `README.md`: 그 단계가 지금 어떻게 동작하고 왜 그렇게 만들었는지 적는다.
  - `log/`: 그 단계의 실행 묶음별 기록.
- `data/`: 데이터셋 배포 파일을 직접 열어 확인한 사실.
- `planning/`: 학습 커리큘럼, 프로젝트 계획, 구현 계획.
- `environment/log/`: 컨테이너 재시작, 시스템 패키지, 줄바꿈 변환처럼 실행 환경에서 생긴 문제의 기록.
  파싱·청킹 품질 문제와 섞지 않는다. 문제 하나마다 파일 하나를 쓴다(아래 "환경 기록").
- `reviews/`: 코드 리뷰 기록. 파일 이름은 `YYYY-MM-DD_<주제>.md`다.

## 단계 README

맨 위에 전체 파이프라인에서의 위치, 구현 코드 위치, 설정 파일 위치를 적는다.
본문에는 데이터 흐름, 결정과 그 이유, 버린 대안, 설정의 의미, 실행 방법, 출력 형식, 알려진 한계,
현재 상태를 적는다.

- 실행 결과 수치와 문제의 경과는 적지 않고 `log/`의 기록으로 링크한다. 다시 실행할 때마다
  README를 고쳐 쓰지 않기 위해서다. 현재 상태는 최신 기록 링크와 한두 문장으로 쓴다.
- 대화에서 정한 결정도 정한 날과 이유를 함께 적는다. 결정을 바꾸면 README를 고치고, 바꾼 계기가 된
  기록을 링크한다.
- 설정값의 원본은 `configs/`의 파일이다. 문서에는 필드의 의미, 단위, 선택 이유를 적는다. 값을 함께
  적었다면 값을 바꾸는 커밋에서 문서도 고친다.
- 출력 형식은 다음 단계가 읽는 계약이다. 필드 이름, 타입, 뜻을 적고 원본 필드와 프로젝트가 만든 필드를
  구분한다. 이 형식을 쓰는 코드와 읽는 코드의 위치를 함께 적고, 형식을 바꾸는 커밋에서 같이 고친다.

## data/

- 맨 위에 확인한 파일, revision, 날짜, 확인 방법을 적는다.
- 직접 확인한 것만 적는다. 논문이나 데이터셋 카드의 설명이 실제 파일과 다르면 문서 안 한 절에 모은다.
  공식 설명을 고쳐 옮기지 않고, 무엇이 어떻게 다른지를 적는다.

## planning/

- 계획은 실행하기 전의 판단이다. 실행 결과는 `log/`에 적고, 계획에는 진행 상태와 링크만 고친다.
- 구현 계획에는 바꿀 파일, 검토한 대안과 고르지 않은 이유, 검증 방법, 모르는 것과 가정한 것을 적는다.

## 단계 기록 (log/)

### 단위와 파일 이름

- 기록 하나는 실행 묶음 하나의 모델(파서) 하나를 다룬다. 같은 목적으로 함께 실행한 VL·Structure 실행은
  한 묶음이고, 모델마다 파일을 나눈다.
- 파일 이름은 `YYYY-MM-DD_<모델>.md`다. 모델은 실행 폴더 이름의 파서 표기(`vl`, `structure`)를 쓴다.
  날짜는 그 묶음의 결과를 처음 기록한 날의 한국 날짜다. 내용이 늘어도 파일 이름은 바꾸지 않는다.
  예: `2026-11-11_vl.md`

### 파일 안의 구성

맨 위에 실행 폴더, 코드 커밋, 같은 묶음의 다른 모델 기록, 이전 묶음의 같은 모델 기록을 적는다.

0. 이슈 요약: 이 기록에서 다룬 이슈의 표. 열은 ID, 모듈, 이슈 유형, 케이스, 현재 상태, 이 기록의 절이다.
   상태는 항상 현재 기준으로 쓴다. 다른 기록에서 해결했거나 원인을 찾은 이슈는 상태 옆에 그 기록 절을 링크한다.
   절 번호는 그 파일 안의 해당 절 제목으로 링크한다.
1. 실행 개요: 목적, 조건(입력, 설정, 코드, 환경, 이전 묶음과 달라진 변수), 결과 요약, 시간·메모리
2. 모듈별 절: 파이프라인 모듈 순서로 나눈다. 파싱은 입력·텍스트층 → 레이아웃 검출·병합 → 영역 인식(VLM·OCR)
   → 표·차트·수식 → 결과 변환·저장 → 후처리(규칙 검사·재인식) 순서다. 청킹은 입력·재인식 적용 → 검사 신호 → 역할 분류
   → 캡션 연결 → 제목 묶음 → 표 변환·길이 맞추기 → 누락 확인 순서다. 문제는 그 문제가 생긴 모듈의 절에 둔다.
   문제가 없던 모듈의 절은 만들지 않는다.
3. 해석과 한계, 다음 단계

### 문제 하나의 구성

원인을 조사한 문제는 모듈 절 안에서 다음 순서로 쓰고, 맨 앞에 현재 상태(아래 "이슈 목록"의 상태 중 하나)를 적는다.
나중 기록에서 해결하면 이 상태 줄도 바꾸고 해결한 기록 절을 링크한다.

1. 어디서 보였나: 증상, 처음 드러난 실행 폴더와 파일, 수치. 다른 단계에서 드러났으면 그 기록을 링크한다.
2. 원인을 어떻게 찾았나: 증상에서 원인까지 거슬러 올라간 순서. 파일·코드·실험으로 확인한 것과
   추론을 나눈다. 실험은 바꾼 변수와 고정한 조건을 적는다.
3. 왜 이 해결책을 골랐나: 후보마다 원인을 직접 해결하는지, 드는 비용, 잃는 것을 적고 고른 이유와
   버린 이유를 쓴다. 당시 판단과 나중에 정리한 해석을 구분한다. 적용 전이면 "미적용"이라고 적는다.
4. 결과: 적용한 실행 폴더, 전후 비교, 해결된 것과 해결되지 않은 것. 다른 변경의 효과가 섞였으면 나눠서 적는다.
5. 남은 문제

관찰만 하고 원인을 조사하지 않은 문제는 모듈 절 안의 표로 모은다. 열은 문제, 관찰과 근거, 원인 확인 수준, 후속이다.

### 여러 묶음·단계에 걸친 문제

- 한 묶음에서 발견하고 다음 묶음에서 고친 문제는 발견한 묶음의 기록에 발견과 당시 원인 판단을 쓰고,
  고친 묶음의 기록에 원인·선택·결과를 쓴다. 서로 링크한다.
- 여러 단계에 걸친 문제는 원인과 수정이 있는 단계의 `log/`에 둔다. 영향을 받은 단계의 기록에는
  그 단계에서 바뀐 것만 적고 링크한다. 예: VL 반복 출력은 파싱 기록에, 청킹에 반영한 결과는 청킹 기록에 둔다.

### 쓰는 규칙

- 수치는 `outputs/<실행 폴더>/`의 `summary.json`·`run.json`에서 옮기고 그 폴더를 링크한다.
  옮기면서 계산을 더했으면 계산 방법을 적는다.
- 근거로 쓴 실험은 일회성이라도 스크립트와 결과를 저장소에 남기고 링크한다. 남기지 못했으면
  그 사실과 실제 위치를 적고 재현할 수 없다고 표시한다.
- 기록의 본문(관찰, 원인 판단, 실행 결과)은 쓴 시점의 사실로 남긴다. 나중에 결론이 바뀌면 그 내용을 본문에
  섞지 않고, 해당 절 끝에 "후속:" 링크로 새 기록을 가리킨다. 오타와 깨진 링크는 고칠 수 있다.
- 상태 표시(이슈 요약의 상태, 문제 절의 "상태:" 줄)는 예외로 항상 현재 기준으로 고친다. 읽는 사람이 어느 기록을
  열어도 그 이슈가 지금 해결됐는지 바로 알 수 있어야 한다.
- 기록을 다른 단위로 나누거나 합칠 때는 문장을 옮기고 위치만 바꾼다. 맨 위에 출처 문서와 커밋을 적는다.
  나눈 파일은 원래 문서와 내용이 달라 git이 이름 변경으로 인식하지 못하므로, 이전 이력은 원래 경로로 찾는다.
- 기록이 가리키는 `outputs/` 실행 폴더는 지우거나 이름을 바꾸지 않는다.

### 타임라인

- 기록을 추가하면 그 단계 `log/README.md`의 타임라인에 날짜순으로 행을 추가한다.
  열은 날짜, 모델, 기록, 핵심, 남은 문제다.
- 핵심에는 그 묶음에서 무엇을 했고 무엇이 바뀌었는지 한두 문장으로 적는다. 타임라인만 읽어도 그 단계가
  어디까지 왔는지 알 수 있게 쓴다.
- 남은 문제의 상태가 바뀌면 타임라인 행도 고친다.

### 이슈 목록

단계 `log/README.md`에는 타임라인과 함께 그 단계의 이슈 목록을 둔다. 여러 기록에 흩어진 이슈를 한곳에서
"무엇이 문제였고, 지금 해결됐는지, 어떻게 해결했는지"로 볼 수 있게 하기 위해서다.

- 계층: 모듈(위 "파일 안의 구성"의 모듈 순서) > 이슈 유형 > 케이스(모델·문서·페이지). 모듈마다 소제목을 두고 표를 나눈다.
- 열: ID, 이슈 유형, 케이스, 상태, 해결 방법·현재 대응, 기록(발견·원인·해결 기록 링크).
  ID는 가장 자세한 기록 절(원인·해결이 있는 절)로 링크해, 목록에서 ID를 누르면 상세 설명으로 넘어가게 한다.
- ID: 단계 머리글자와 두 자리 번호다(파싱 `P-01`, 청킹 `C-01`). 한 번 붙인 ID는 바꾸거나 다시 쓰지 않는다.
  같은 이슈는 모든 기록에서 같은 ID로 부른다. 원인이 다른 단계에 있는 이슈는 그 단계의 ID를 함께 적는다.
- 상태는 다음 중 하나다. 표 위에 상태별 수를 적는다.

| 상태 | 뜻 |
|---|---|
| 해결 | 원인에 대응했고 결과에서 확인했다 |
| 부분 해결 | 일부 케이스만 해결했다 |
| 표시만 | 원인은 그대로 두고 신호로 드러낸다 |
| 미해결 | 원인을 조사했거나 알지만 대응하지 않았다 |
| 관찰만 | 원인을 조사하지 않았다 |
| 한계 | 구현 방식에서 오는 알려진 제약이다 |
| 정상 동작 | 의도대로 동작했고 대응할 필요가 없다 |

- 실행 환경 문제는 `environment/log/README.md`에 `E-01`처럼 ID를 붙여 같은 상태 용어로 관리한다.

### 남은 이슈

- 해결과 정상 동작을 뺀 모든 이슈(파싱·청킹·실행 환경)는 루트 `README.md`의 "남은 이슈" 절에 한 표로 모은다.
  열은 ID(상세 기록 링크), 단계·모듈, 이슈, 케이스, 상태, 현재 대응이고, 상태 순서(미해결 → 부분 해결 → 표시만
  → 관찰만 → 한계)로 놓는다. 표 위에 상태별 수를 적는다.
- 이슈 상태가 바뀌면 같은 커밋에서 다음을 모두 고친다. 하나라도 빠지면 문서끼리 상태가 달라진다.
  1. 그 이슈가 나오는 모든 기록의 이슈 요약 상태와 문제 절의 "상태:" 줄
  2. 단계 `log/README.md`의 이슈 목록, 상태별 수, 타임라인의 남은 문제
  3. 루트 `README.md`의 남은 이슈 표와 상태별 수
- 이슈를 해결하는 변경과 그 이슈의 상태 갱신은 같은 PR에 넣는다. 그 이슈의 문서가 아직 머지되지 않은 다른 PR에
  있으면, 해결 PR을 먼저 머지한 뒤 문서 PR을 머지하기 전에 상태를 고친다. 머지 뒤로 미루지 않는다.
  PR 검사는 문서끼리 상태가 같은지만 보고 코드가 이미 고쳐졌는지는 모르므로, 늦게 고친 상태를 잡지 못한다.
- 해결된 이슈는 루트 `README.md`의 남은 이슈 표에서 빼고, 단계 이슈 목록에는 "해결"로 남긴다.
- 대조 자료의 한계처럼 대응 대상이 아닌 제약은 이슈로 세지 않고, 목록 아래에 어디에 적혀 있는지만 링크한다.

## 환경 기록 (environment/log/)

- 문제 하나마다 파일 하나다. 파일 이름은 `YYYY-MM-DD_<주제>.md`이고 날짜는 처음 기록한 날의 한국 날짜다.
  주제는 영어 소문자로 쓰고 단어를 `-`로 잇는다.
- 구성은 위 "문제 하나의 구성"과 같다. 맨 위에 ID, 현재 상태, 관련 실행 폴더, 코드 커밋을 적는다.
- `environment/log/README.md` 표의 열은 ID, 날짜, 기록, 상태, 핵심이다. ID는 `E-01`처럼 붙이고 바꾸지 않는다.

## 그림

그림은 Mermaid `flowchart`로 그린다. GitHub와 대부분의 Markdown 뷰어가 이 코드 블록을 그림으로 보여 준다.
그림 종류에 따라 노드와 화살표가 뜻하는 것이 다르므로, 절 제목과 그림 앞 문장에 종류를 밝힌다.

| 종류 | 보여 주는 것 | 노드 | 화살표 |
|---|---|---|---|
| 데이터 흐름(파이프라인) | 데이터가 어떤 형태로 바뀌며 어디에 저장되는가 | 데이터: 이름·형식·크기·저장 위치 | 그 데이터를 바꾸는 모듈·함수와 하는 일 |
| 호출 순서 | 코드가 어떤 순서로 실행되는가 | 모듈·함수 | 실행 순서 |
| 판단 순서 | 조건에 따라 처리가 어떻게 갈라지는가 | 조건(마름모)과 결과 | 조건의 답 |

- 단계 README와 기록의 흐름 그림은 데이터 흐름으로 그린다. 모듈·파일을 실행 순서대로 늘어놓은 그림을
  데이터 흐름이나 파이프라인이라고 부르지 않는다. 호출 순서가 따로 필요할 때만 "호출 순서"라는 이름으로 그린다.
- 데이터 흐름에서 파일로 저장되는 데이터는 원통(`[( )]`), 메모리에만 있는 중간 데이터는 둥근 사각형(`( )`),
  설정·입력 목록은 평행사변형(`[/ /]`)으로 그린다.
- 문제 하나를 설명할 때는 그 문제의 실제 데이터(크기·토큰 수·파일)가 어떻게 바뀌었는지 따라가는 데이터 흐름으로 그린다.
- 문서 맨 위의 한 줄 위치 표시(`PDF → 파싱〔현재〕 → …`)는 루트 AGENTS.md 형식대로 텍스트로 둔다.
- 화살표 이름에는 실제 모듈·함수 이름을 쓴다. 확인하지 못한 추론은 점선 화살표나 점선 테두리로 구분한다.
- 기록의 그림은 그 기록을 쓴 시점에 알던 사실로만 그린다.
- 노드 글자에 꺾쇠(`<`, `>`)를 쓰지 않는다. HTML 태그로 해석돼 글자가 사라질 수 있다. 줄바꿈은 `<br/>`만 쓴다.
- 선이 엇갈리지 않게 그린다. 주 흐름은 한 줄기(위→아래 또는 왼쪽→오른쪽)로 잇고, 곁가지로 저장되는 파일은
  만드는 데이터 바로 옆에 점선으로 붙인다. 먼 노드끼리 잇는 선이 필요하면 그림을 나누거나 노드를 합친다.
- 선 라벨은 번호와 함수 이름만 짧게 쓰고, 함수 위치와 하는 일은 그림 아래 표(화살표 번호 · 함수 · 하는 일)로 쓴다.
- 그림을 추가하거나 고치면 커밋 전에 렌더링해 선 엇갈림, 상자 겹침, 잘린 글자가 없는지 눈으로 확인한다.
  `tools/diagram_check.py`가 렌더링 실패, 선 교차, 상자·라벨 관통, 상자·묶음 상자·라벨 겹침, 꺾쇠, 긴 선 라벨을
  PR마다 검사한다(루트 README "PR 문서 검사"). 이 검사로 잡지 못하는 보기 좋음(지나친 우회, 읽는 순서)은 눈으로 본다.
  렌더링하지 못했으면 커밋 메시지와 보고에 그 사실을 적는다.

## 이동과 링크

- 문서 사이 링크는 상대 경로로 쓴다.
- 문서를 옮기거나 이름을 바꿀 때는 `git mv`를 쓰고, 그 문서를 가리키는 링크(README.md, 다른 문서,
  코드 주석)를 같은 커밋에서 고친다. 커밋 전에 옛 경로를 저장소 전체에서 검색해 남은 곳이 없는지 확인한다.
