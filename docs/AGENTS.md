# docs 작업 지침

문서 전반과 글쓰기 규칙은 루트 AGENTS.md를 따른다. 여기에는 docs/ 안에서만 쓰는 규칙을 적는다.

## 구조

- `<단계>/`: 파이프라인 단계별 문서. 지금은 `parsing/`, `chunking/`이 있고, 다음 단계 작업을 시작할 때
  같은 형식으로 만든다.
  - `README.md`: 그 단계가 지금 어떻게 동작하고 왜 그렇게 만들었는지 적는다.
  - `log/`: 그 단계에서 생긴 문제와 실행의 기록.
- `data/`: 데이터셋 배포 파일을 직접 열어 확인한 사실.
- `planning/`: 학습 커리큘럼, 프로젝트 계획, 구현 계획.
- `environment/log/`: 컨테이너 재시작, 시스템 패키지, 줄바꿈 변환처럼 실행 환경에서 생긴 문제의 기록.
  파싱·청킹 품질 문제와 섞지 않는다. 형식은 단계 `log/`와 같다.
- `reviews/`: 코드 리뷰 기록. 파일 이름은 `YYYY-MM-DD_<주제>.md`다.

## 단계 README

맨 위에 전체 파이프라인에서의 위치, 구현 코드 위치, 설정 파일 위치를 적는다.
본문에는 처리 흐름, 결정과 그 이유, 버린 대안, 설정의 의미, 실행 방법, 출력 형식, 알려진 한계,
현재 상태를 적는다.

- 실행 결과 수치와 문제의 경과는 적지 않고 `log/`의 기록으로 링크한다. 다시 실행할 때마다
  README를 고쳐 쓰지 않기 위해서다. 현재 상태는 최신 기록 링크와 한두 문장으로 쓴다.
- 대화에서 정한 결정도 정한 날과 이유를 함께 적는다. 결정을 바꾸면 README를 고치고, 바꾼 계기가 된
  기록을 링크한다.
- 설정값의 원본은 `configs/`의 파일이다. 문서에는 필드의 의미, 단위, 선택 이유를 적는다. 값을 함께
  적었다면 값을 바꾸는 커밋에서 문서도 고친다.
- 출력 형식은 다음 단계가 읽는 계약이다. 필드 이름, 타입, 뜻을 적고 원본 필드와 프로젝트가 만든 필드를
  구분한다. 이 형식을 쓰는 코드와 읽는 코드의 위치를 함께 적고, 형식을 바꾸는 커밋에서 같이 고친다.

## data/

- 맨 위에 확인한 파일, revision, 날짜, 확인 방법을 적는다.
- 직접 확인한 것만 적는다. 논문이나 데이터셋 카드의 설명이 실제 파일과 다르면 문서 안 한 절에 모은다.
  공식 설명을 고쳐 옮기지 않고, 무엇이 어떻게 다른지를 적는다.

## planning/

- 계획은 실행하기 전의 판단이다. 실행 결과는 `log/`에 적고, 계획에는 진행 상태와 링크만 고친다.
- 구현 계획에는 바꿀 파일, 검토한 대안과 고르지 않은 이유, 검증 방법, 모르는 것과 가정한 것을 적는다.

## 기록 (log/)

### 종류와 단위

- 문제 기록: 문제 하나를 다룬다. 문제가 여러 실행에 걸쳐도(재파싱 → 원인 조사 → 수정 → 다시 실행)
  한 문서에 이어 쓴다. 한 번의 조사에서 문제를 여러 개 찾았으면 문제마다 나누고 서로 링크한다.
- 실행 기록: 다룰 문제 없이 실행 결과만 남길 때 쓴다. 예: 첫 실행, 설정 하나를 바꾼 비교 실행.
- 여러 단계에 걸친 문제는 원인과 수정이 있는 단계의 `log/`에 둔다. 영향을 받은 단계의 기록에는
  그 단계에서 바뀐 것만 적고 링크한다. 예: VL 반복 출력은 `parsing/log/`에, 청킹에 반영한 결과는
  `chunking/log/`에 둔다.

### 파일 이름

`YYYY-MM-DD_<주제>.md`로 짓는다. 날짜는 기록을 처음 쓴 날의 한국 날짜다. 주제는 영어 소문자로 쓰고
단어를 `-`로 잇는다. 내용이 늘어도 파일 이름은 바꾸지 않는다.
예: `2026-11-11_vl-generation-limit-repetition.md`

### 문제 기록의 구성

맨 위에 상태(해결·부분 해결·미해결), 관련 실행 폴더, 코드 커밋을 적는다.

1. 문제가 어디서 보였나: 증상, 처음 드러난 실행 폴더와 파일, 수치. 다른 단계에서 드러났으면
   그 단계의 기록을 링크한다.
2. 원인을 어떻게 찾았나: 증상에서 원인까지 거슬러 올라간 순서. 파일·코드·실험으로 확인한 것과
   추론을 나눈다. 실험은 바꾼 변수와 고정한 조건을 적는다.
3. 왜 이 해결책을 골랐나: 후보마다 원인을 직접 해결하는지, 드는 비용, 잃는 것을 적고 고른 이유와
   버린 이유를 쓴다. 당시 판단과 나중에 정리한 해석을 구분한다.
4. 결과: 적용한 실행 폴더, 전후 비교, 해결된 것과 해결되지 않은 것. 다른 변경의 효과가 섞였으면
   나눠서 적는다.
5. 남은 문제와 다음 단계

해결 전이면 3·4절에 "미적용"이라고 적고 절을 지우지 않는다. 어디까지 진행됐는지 보이게 하기 위해서다.

### 실행 기록의 구성

1. 목적: 무엇을 확인하려고 실행했나
2. 조건: 입력, 설정 파일과 해시, 코드 커밋, 실행 환경, 이전 실행과 달라진 변수
3. 결과
4. 이전 실행과 비교
5. 해석과 한계

### 쓰는 규칙

- 수치는 `outputs/<실행 폴더>/`의 `summary.json`·`run.json`에서 옮기고 그 폴더를 링크한다.
  옮기면서 계산을 더했으면 계산 방법을 적는다.
- 근거로 쓴 실험은 일회성이라도 스크립트와 결과를 저장소에 남기고 링크한다. 남기지 못했으면
  그 사실과 실제 위치를 적고 재현할 수 없다고 표시한다.
- 기록은 쓴 시점의 사실로 남긴다. 나중에 결론이 바뀌면 이전 본문을 고쳐 쓰지 않고 새 기록을 만들어
  서로 링크한다. 이전 기록에서는 상태와 "후속:" 링크만 고친다. 오타와 깨진 링크는 고칠 수 있다.
- 기록이 가리키는 `outputs/` 실행 폴더는 지우거나 이름을 바꾸지 않는다.

### 타임라인

- 기록을 추가하면 그 단계 `log/README.md`의 타임라인에 날짜순으로 행을 추가한다.
  열은 날짜, 기록, 종류(문제·실행), 상태, 핵심이다.
- 핵심에는 무엇이 문제였고 무엇을 정했는지 한두 문장으로 적는다. 타임라인만 읽어도 그 단계가
  어디까지 왔는지 알 수 있게 쓴다.
- 기록의 상태가 바뀌면 타임라인 행도 고친다.

## 이동과 링크

- 문서 사이 링크는 상대 경로로 쓴다.
- 문서를 옮기거나 이름을 바꿀 때는 `git mv`를 쓰고, 그 문서를 가리키는 링크(README.md, 다른 문서,
  코드 주석)를 같은 커밋에서 고친다. 커밋 전에 옛 경로를 저장소 전체에서 검색해 남은 곳이 없는지 확인한다.
