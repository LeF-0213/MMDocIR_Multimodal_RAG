# docs 작업 지침

문서 전반과 글쓰기 규칙은 루트 AGENTS.md를 따른다. 여기에는 docs/ 안에서만 쓰는 규칙을 적는다.

## 구조

- `<단계>/`: 파이프라인 단계별 문서. 지금은 `parsing/`, `chunking/`이 있고, 다음 단계 작업을 시작할 때
  같은 형식으로 만든다.
  - `README.md`: 그 단계가 지금 어떻게 동작하고 왜 그렇게 만들었는지 적는다.
  - `log/`: 그 단계의 실행 묶음별 기록.
- `data/`: 데이터셋 배포 파일을 직접 열어 확인한 사실.
- `planning/`: 학습 커리큘럼, 프로젝트 계획, 구현 계획.
- `environment/log/`: 컨테이너 재시작, 시스템 패키지, 줄바꿈 변환처럼 실행 환경에서 생긴 문제의 기록.
  파싱·청킹 품질 문제와 섞지 않는다. 문제 하나마다 파일 하나를 쓴다(아래 "환경 기록").
- `reviews/`: 코드 리뷰 기록. 파일 이름은 `YYYY-MM-DD_<주제>.md`다.

## 단계 README

맨 위에 전체 파이프라인에서의 위치, 구현 코드 위치, 설정 파일 위치를 적는다.
본문에는 처리 흐름, 결정과 그 이유, 버린 대안, 설정의 의미, 실행 방법, 출력 형식, 알려진 한계,
현재 상태를 적는다.

- 실행 결과 수치와 문제의 경과는 적지 않고 `log/`의 기록으로 링크한다. 다시 실행할 때마다
  README를 고쳐 쓰지 않기 위해서다. 현재 상태는 최신 기록 링크와 한두 문장으로 쓴다.
- 대화에서 정한 결정도 정한 날과 이유를 함께 적는다. 결정을 바꾸면 README를 고치고, 바꾼 계기가 된
  기록을 링크한다.
- 설정값의 원본은 `configs/`의 파일이다. 문서에는 필드의 의미, 단위, 선택 이유를 적는다. 값을 함께
  적었다면 값을 바꾸는 커밋에서 문서도 고친다.
- 출력 형식은 다음 단계가 읽는 계약이다. 필드 이름, 타입, 뜻을 적고 원본 필드와 프로젝트가 만든 필드를
  구분한다. 이 형식을 쓰는 코드와 읽는 코드의 위치를 함께 적고, 형식을 바꾸는 커밋에서 같이 고친다.

## data/

- 맨 위에 확인한 파일, revision, 날짜, 확인 방법을 적는다.
- 직접 확인한 것만 적는다. 논문이나 데이터셋 카드의 설명이 실제 파일과 다르면 문서 안 한 절에 모은다.
  공식 설명을 고쳐 옮기지 않고, 무엇이 어떻게 다른지를 적는다.

## planning/

- 계획은 실행하기 전의 판단이다. 실행 결과는 `log/`에 적고, 계획에는 진행 상태와 링크만 고친다.
- 구현 계획에는 바꿀 파일, 검토한 대안과 고르지 않은 이유, 검증 방법, 모르는 것과 가정한 것을 적는다.

## 단계 기록 (log/)

### 단위와 파일 이름

- 기록 하나는 실행 묶음 하나의 모델(파서) 하나를 다룬다. 같은 목적으로 함께 실행한 VL·Structure 실행은
  한 묶음이고, 모델마다 파일을 나눈다.
- 파일 이름은 `YYYY-MM-DD_<모델>.md`다. 모델은 실행 폴더 이름의 파서 표기(`vl`, `structure`)를 쓴다.
  날짜는 그 묶음의 결과를 처음 기록한 날의 한국 날짜다. 내용이 늘어도 파일 이름은 바꾸지 않는다.
  예: `2026-11-11_vl.md`

### 파일 안의 구성

맨 위에 실행 폴더, 코드 커밋, 같은 묶음의 다른 모델 기록, 이전 묶음의 같은 모델 기록을 적는다.

1. 실행 개요: 목적, 조건(입력, 설정, 코드, 환경, 이전 묶음과 달라진 변수), 결과 요약, 시간·메모리
2. 모듈별 절: 파이프라인 모듈 순서로 나눈다. 파싱은 입력·텍스트층 → 레이아웃 검출·병합 → 영역 인식(VLM·OCR)
   → 표·차트·수식 → 결과 변환·저장 → 후처리(규칙 검사·재인식) 순서다. 문제는 그 문제가 생긴 모듈의 절에 둔다.
   문제가 없던 모듈의 절은 만들지 않는다.
3. 해석과 한계, 다음 단계

### 문제 하나의 구성

원인을 조사한 문제는 모듈 절 안에서 다음 순서로 쓰고, 맨 앞에 상태(해결·부분 해결·미해결)를 적는다.

1. 어디서 보였나: 증상, 처음 드러난 실행 폴더와 파일, 수치. 다른 단계에서 드러났으면 그 기록을 링크한다.
2. 원인을 어떻게 찾았나: 증상에서 원인까지 거슬러 올라간 순서. 파일·코드·실험으로 확인한 것과
   추론을 나눈다. 실험은 바꾼 변수와 고정한 조건을 적는다.
3. 왜 이 해결책을 골랐나: 후보마다 원인을 직접 해결하는지, 드는 비용, 잃는 것을 적고 고른 이유와
   버린 이유를 쓴다. 당시 판단과 나중에 정리한 해석을 구분한다. 적용 전이면 "미적용"이라고 적는다.
4. 결과: 적용한 실행 폴더, 전후 비교, 해결된 것과 해결되지 않은 것. 다른 변경의 효과가 섞였으면 나눠서 적는다.
5. 남은 문제

관찰만 하고 원인을 조사하지 않은 문제는 모듈 절 안의 표로 모은다. 열은 문제, 관찰과 근거, 원인 확인 수준, 후속이다.

### 여러 묶음·단계에 걸친 문제

- 한 묶음에서 발견하고 다음 묶음에서 고친 문제는 발견한 묶음의 기록에 발견과 당시 원인 판단을 쓰고,
  고친 묶음의 기록에 원인·선택·결과를 쓴다. 서로 링크한다.
- 여러 단계에 걸친 문제는 원인과 수정이 있는 단계의 `log/`에 둔다. 영향을 받은 단계의 기록에는
  그 단계에서 바뀐 것만 적고 링크한다. 예: VL 반복 출력은 파싱 기록에, 청킹에 반영한 결과는 청킹 기록에 둔다.

### 쓰는 규칙

- 수치는 `outputs/<실행 폴더>/`의 `summary.json`·`run.json`에서 옮기고 그 폴더를 링크한다.
  옮기면서 계산을 더했으면 계산 방법을 적는다.
- 근거로 쓴 실험은 일회성이라도 스크립트와 결과를 저장소에 남기고 링크한다. 남기지 못했으면
  그 사실과 실제 위치를 적고 재현할 수 없다고 표시한다.
- 기록은 쓴 시점의 사실로 남긴다. 나중에 결론이 바뀌면 그 내용을 본문에 섞지 않고, 해당 절 끝에
  "후속:" 링크로 새 기록을 가리킨다. 오타와 깨진 링크는 고칠 수 있다.
- 기록을 다른 단위로 나누거나 합칠 때는 문장을 옮기고 위치만 바꾼다. 맨 위에 출처 문서와 커밋을 적는다.
  나눈 파일은 원래 문서와 내용이 달라 git이 이름 변경으로 인식하지 못하므로, 이전 이력은 원래 경로로 찾는다.
- 기록이 가리키는 `outputs/` 실행 폴더는 지우거나 이름을 바꾸지 않는다.

### 타임라인

- 기록을 추가하면 그 단계 `log/README.md`의 타임라인에 날짜순으로 행을 추가한다.
  열은 날짜, 모델, 기록, 핵심, 남은 문제다.
- 핵심에는 그 묶음에서 무엇을 했고 무엇이 바뀌었는지 한두 문장으로 적는다. 타임라인만 읽어도 그 단계가
  어디까지 왔는지 알 수 있게 쓴다.
- 남은 문제의 상태가 바뀌면 타임라인 행도 고친다.

## 환경 기록 (environment/log/)

- 문제 하나마다 파일 하나다. 파일 이름은 `YYYY-MM-DD_<주제>.md`이고 날짜는 처음 기록한 날의 한국 날짜다.
  주제는 영어 소문자로 쓰고 단어를 `-`로 잇는다.
- 구성은 위 "문제 하나의 구성"과 같다. 맨 위에 상태, 관련 실행 폴더, 코드 커밋을 적는다.
- `environment/log/README.md` 타임라인의 열은 날짜, 기록, 상태, 핵심이다.

## 그림

- 여러 모듈이나 단계를 거치는 흐름(처리 흐름, 문제가 생긴 경로와 대응한 경로)은 Mermaid `flowchart`로 그린다.
  GitHub와 대부분의 Markdown 뷰어가 이 코드 블록을 그림으로 보여 준다.
- 문서 맨 위의 한 줄 위치 표시(`PDF → 파싱〔현재〕 → …`)는 루트 AGENTS.md 형식대로 텍스트로 둔다.
- 노드 이름에는 실제 파일·함수 이름을 쓴다. 확인하지 못한 추론은 점선 화살표나 점선 테두리로 구분한다.
- 노드 글자에 꺾쇠(`<`, `>`)를 쓰지 않는다. HTML 태그로 해석돼 글자가 사라질 수 있다. 줄바꿈은 `<br/>`만 쓴다.

## 이동과 링크

- 문서 사이 링크는 상대 경로로 쓴다.
- 문서를 옮기거나 이름을 바꿀 때는 `git mv`를 쓰고, 그 문서를 가리키는 링크(README.md, 다른 문서,
  코드 주석)를 같은 커밋에서 고친다. 커밋 전에 옛 경로를 저장소 전체에서 검색해 남은 곳이 없는지 확인한다.
