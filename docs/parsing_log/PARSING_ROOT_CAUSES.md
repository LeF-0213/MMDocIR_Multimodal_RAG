# 재파싱 후 남은 문제의 원인 조사

조사: 2026-11-11. 대상: [병합 해제 재파싱 결과](REPARSE_RESULT.md)에 남은 문제와 재파싱 중 생긴 실행 환경 문제.
설치 패키지: PaddleOCR 3.7.0·PaddleX 3.7.2·PaddlePaddle 3.3.1. 모델 파일: `~/.paddlex/official_models/`.

```text
PDF → 파싱〔남은 문제의 원인 조사〕 → 청킹 → 임베딩 → 인덱스 → 검색·평가
```

각 문제를 **확인한 사실**과 **추론**으로 나눈다.

- 사실: 저장된 결과 파일, 원본 PDF, 설치된 라이브러리 코드, 모델 설정 파일, 실행 기록, 통제 실험에서 직접 확인한 것.
- 추론: 사실로 확정하지 못해 근거를 들어 판단한 것. 무엇을 확인하지 못했는지 함께 적는다.

이 문서는 원인 조사다. 해결책을 적용하거나 효과를 측정하지 않았다.
8절의 대응 후보는 아직 실험하지 않은 제안이다.

## 2. VL 반복 생성: Toyota p2·p7, 슬라이드 0e94 p6

### 2.1 세 블록의 공통점 (사실)

- 27페이지의 VL 블록 445개를 모델과 같은 `tokenizer.json`으로 세면, 4,096토큰인 블록은 정확히 3개다.
  나머지 중 가장 긴 블록은 3,537토큰(RAG 논문 p6 표)이다. 기준 실행과 새 실행이 같다.

  | 페이지·블록 | 라벨 | VLM 프롬프트 | 출력 | 페이지 처리 시간 |
  |---|---|---|---|---|
  | Toyota p2 블록 20 | `image` | `OCR:` | 제목 한 줄 뒤 원본에 없는 문장, "China" 2,029회 | 1,902초 |
  | Toyota p7 블록 15 | `image` | `OCR:` | 영어 라벨 6개와 일본어 한 구절 뒤 "1. 2. 3. … 834." | 1,989초 |
  | 슬라이드 p6 블록 0 | `chart` | `Chart Recognition:` | "Item \| Value" 표에 1~698번 행, 값은 거의 빈칸 | 1,778초 |

- 세 페이지는 새 실행에서 처리 시간이 가장 긴 1~3위다.
- 세 출력 모두 문장이나 행 중간에서 끝난다. 종료 토큰 없이 한도에서 잘렸다.
- 기준 실행(Windows)과 새 실행(Linux 컨테이너)의 세 출력이 글자 단위까지 같다. 같은 입력이면 같은 출력이 나오는 결정적 디코딩이다.

### 2.2 생성 설정 (사실, 설치된 코드)

- 생성 한도: PaddleX `paddleocr_vl/pipeline.py`의 `_paddleocr_vl_run_vl_recognition_batches()`가
  `max_new_tokens`를 지정하지 않으면 4,096으로 채운다. 프로젝트의 `predict_options()`는 `layout_shape_mode`만 넘긴다.
- 반복 억제·샘플링: `doc_vlm/predictor.py`의 로컬 모델 경로는 `repetition_penalty`·`temperature`·`top_p`를 받으면
  "not supported by the local model and will be ignored" 경고만 내고 무시한다.
- 디코딩 방식: 생성 설정 기본값이 `num_beams=1`이고 sampling을 켜지 않으므로 `greedy_search`다
  (`common/transformers/generation/configuration_utils.py`의 `_get_generation_mode()`).
- 모델의 `generation_config.json`에는 `eos_token_id`·`pad_token_id`만 있고 반복 관련 값이 없다.

### 2.3 이 블록들이 VLM에 들어간 이유 (사실)

- PaddleX는 `use_ocr_for_image_block=False`이면 `image`·`header_image`·`footer_image`를,
  `use_chart_recognition=False`이면 `chart`를 VLM 인식 대상에서 뺀다(`pipeline.py`의 `image_labels`).
- 공식 설정(`PaddleOCR-VL-1.6.yaml`)과 코드 기본값은 둘 다 `False`다.
- 프로젝트 `parsing/vl_parser.py`는 그림 속 글자와 그래프를 다루려고 두 값을 모두 `True`로 바꿨다.
  그래서 세 블록이 `OCR:`·`Chart Recognition:` 프롬프트로 VLM에 들어갔다.
- 공식 기본값이었다면 세 블록은 VLM을 거치지 않는다. 그 대신 그림 속 글자도 얻지 못한다.

### 2.4 Toyota p2: 입력 해상도 (사실)

- 블록 20은 보고서 한 페이지 전체를 줄인 미리보기 그림이다. PDF 영역은 132.5×97pt이고,
  144 DPI 페이지 이미지에서 265×194px(51,410픽셀)다.
- 원본 PDF에서 이 영역은 래스터 그림이 아니라 벡터와 텍스트로 그려져 있다. 텍스트층에 실제 문장 1,065단어가 있고,
  글자 크기는 대부분 1.23pt다. 144 DPI에서 글자 높이가 약 2.5px로, 사람도 읽을 수 없다.
- 미리보기 제목(2.62pt, 약 5px)은 모델 출력의 첫 줄과 같다.
- 실제 텍스트층에서 "China"는 한 번 나온다("Europe, North America, and China by the same year").
- 픽셀 하한이 112,896이라 PaddleX가 이 crop을 약 1.48배(선형) 키워 넣는다. 키워도 새 정보는 생기지 않는다.

### 2.5 Toyota p2: 해상도만 바꾼 통제 실험 (사실)

같은 모델(PaddleOCR-VL-1.6-0.9B), 같은 `OCR:` 프롬프트, 같은 픽셀 하한·상한(112,896·1,003,520)에
같은 영역을 해상도만 바꿔 넣었다. 컨테이너 CPU에서 PaddleX `create_model`로 인식 모델만 불러 실행했다.

- 실험 스크립트와 결과 JSON은 저장소에 넣지 않았다. 결과 JSON은 컨테이너 `~/rootcause/`에 있다.
- 비교 기준은 원본 PDF 텍스트층의 이 영역 글자(1,065단어)다. 겹침은 2절의 텍스트층 토큰 겹침과 같은 대리 지표이며 정답 정확도가 아니다.

| 입력 | 크기(px) | 생성 결과 | 끝난 방식 | 텍스트층 재현율 / 정밀도 |
|---|---|---|---|---|
| 저장된 144 DPI 페이지 PNG에서 자른 영역 | 265×194 | 파이프라인 출력과 같은 "China" 반복 | 재현 확인용 한도 512토큰에 닿음 | 0.01 / 0.06 |
| 원본 PDF를 288 DPI로 다시 렌더링 | 530×388 | 제목·날짜 뒤 원본에 없는 번호 목록을 129번까지 반복 | 4,095토큰(한도 근처, 문장 중간에서 끊김) | 0.16 / 0.06 |
| 원본 PDF를 576 DPI로 다시 렌더링 | 1060×776 | 미리보기 본문을 차례대로 옮김. "China" 1회, 끝에 쪽 바닥글 | 1,166토큰에서 스스로 종료 | 0.79 / 0.98 |

- 재현 확인: 144 DPI 조건 출력의 512토큰이 파이프라인 출력의 앞 512토큰과 토큰 단위로 같다.
  실험 입력이 파이프라인 입력과 같다는 근거다.
- 576 DPI에서만 반복 없이 끝났다. 288 DPI는 글자를 일부 읽었지만(날짜 "December 14, 2021" 등) 다시 반복에 빠졌다.

색 순서도 확인했다. 첫 실험은 RGB 배열을 넣어 144 DPI 출력이 파이프라인과 달랐고, 다시 실행해 위 결과를 얻었다.

- 프로젝트는 PaddleOCR 관례대로 BGR 페이지 배열을 넘긴다(`parsing/pdf_parser.py`).
- PaddleX VL 파이프라인은 이 배열에서 블록을 잘라 색 변환 없이 VLM에 넘긴다.
- 로컬 처리기 `fetch_image()`는 배열을 `Image.fromarray()`로 그대로 읽는다.
- 그래서 파이프라인에서 VLM은 빨강·파랑 채널이 바뀐 이미지를 받는다.
- RGB로 넣은 첫 실험도 해상도에 따른 결과는 같았다. 144·288 DPI는 반복, 576 DPI는 1,326토큰에서 종료(재현율 0.89·정밀도 0.95)였다.

### 2.6 Toyota p7·슬라이드 p6 (사실)

- Toyota p7 블록 15는 일본어 손글씨가 섞인 원뿔 도식 그림이다. 모델은 영어 라벨 6개와 일본어 "国民的支持"
  (그림 속 표기는 "国民の支持")를 출력한 뒤 번호 나열로 넘어갔다.
- 슬라이드 p6 블록 0은 1957~1975년 우주 경쟁 연표 그림이다. 행·열 데이터가 있는 차트가 아니다.
  모델은 "Item | Value" 표를 만들고 58~61번 행에만 그림 속 이름(Sputnik·Vostok·X-15)과 비슷한 값을 넣었다.

### 2.7 원인 판단

- 사실로 확정한 것:
  - 세 출력은 반복 루프가 생성 한도 4,096토큰까지 이어진 결과다.
  - 반복을 끊을 수 있는 인자(`repetition_penalty`)는 현재 로컬 경로에서 적용되지 않는다.
  - 세 블록이 VLM에 들어간 것은 프로젝트가 켠 두 옵션 때문이다.
  - Toyota p2의 반복은 입력 해상도 때문이다. 같은 모델·프롬프트·입력 방식에서 해상도만 576 DPI로 올리면
    반복 없이 원문을 옮기고 스스로 끝난다. 144 DPI에서는 본문 글자 높이가 약 2.5px라 읽을 정보가 없다.
- 추론:
  - 읽을 정보가 부족한 입력에서 greedy 디코딩이 그럴듯한 시작 뒤 같은 토큰열을 반복하는 상태에 갇히는 것으로 본다.
    Toyota p2에서 해상도가 이 상태를 바꾼다는 것은 확인했지만, 모델 내부에서 반복이 시작되는 이유는 확인하지 않았다.
  - Toyota p7·슬라이드 p6은 실험하지 않았다. Toyota p7은 손글씨 일본어가 작게 들어간 도식이고,
    슬라이드 p6은 표로 옮길 데이터가 없는 연표다. 해상도 부족이나 프롬프트와 그림 형태의 불일치가 원인이라고 판단하지만 확인하지 않았다.
  - 576 DPI 조건에서 RGB 입력의 재현율(0.89)이 BGR 입력(0.79)보다 높았다. 블록 하나의 결과이므로 채널 순서가 전체 인식 품질에 주는 영향은 판단하지 않는다.

## 3. Structure 차트 환각: 슬라이드 0e94 p6

- 사실:
  - Structure는 같은 연표 그림을 `chart`로 검출하고 PP-Chart2Table로 표를 만들었다. 출력은 63행 "ID | Name | Year | Value"다.
  - 5행부터 이름이 "Lunar Vinyus"로 반복되고, 연도는 58에서 121까지 1씩 증가한다.
  - 그림의 연도축은 58~76이고 "Lunar Vinyus"라는 항목은 없다. 77~121년과 이 이름은 원본에 없는 값이다.
  - 출력은 PP-Chart2Table의 `tokenizer.json`으로 962토큰이다. 이 모델의 기본 생성 한도(`GOT_ocr_2_0.py`의 `PPChart2TableInference`, 1,024)에 닿지 않았다.
  - 기준 실행과 새 실행의 출력이 같다.
- 추론: VL과 같은 "한도에서 잘림"은 아니다. 데이터 표가 없는 그림을 차트→표 모델에 넣어, 표 형식에 맞춰 값을 지어낸 결과로 본다. 모델이 왜 63행에서 멈췄는지는 확인하지 않았다.

## 4. Structure 표 격자 신호

### 4.1 RAG 논문 p6: 표 구조 토큰 상한 (사실)

- 원본 표(Table I)의 마지막 부분에는 SANTA부터 G-Retriever까지 11개 행이 따로 있다.
- 출력은 63행이고, 마지막 63번째 행만 칸이 4개다(다른 행은 6개). 이 4칸에 11개 행의 방법명·데이터 출처·형식·단위가 이어 붙어 있다.
- 표 구조 모델(SLANet_plus·SLANeXt_wired)의 `inference.yml`은 `max_text_length: 500`이다.
- 출력 HTML에서 구조 토큰을 모델 사전(`<td></td>`를 한 토큰으로 묶는 `merge_no_span_structure: true`) 기준으로 다시 세면 501개로, 상한과 같은 수준이다.
  같은 실행의 다른 표는 47~197개다.
- 디코더는 정해진 길이만큼만 구조 토큰을 낸다(`table_structure_recognition/processors.py`의 `decode()`).
- 판단(사실): 구조 토큰이 상한에 닿아 63번째 행의 4번째 칸 뒤에서 잘렸다. 그 아래 행의 OCR 글자가 남은 마지막 칸들에 배정됐다.

### 4.2 Toyota p32: 레이아웃 검출이 두 구조를 하나로 묶음 (사실)

- 이 영역의 레이아웃 검출 결과는 `table` 상자 하나(신뢰도 0.97, 이미지 좌표 697,621–1632,1152)다.
- 이 상자 안에 서로 다른 두 구조가 있다. 위쪽은 2010~2021 기간별 막대 연표 표이고, 아래쪽은 날짜와 글머리표가 있는 두 열의 목록이다.
- 표 인식은 두 구조를 6열 격자 하나로 만들었다. 11~19행에 왼쪽 목록(April 2011 등)과 오른쪽 목록(April 2017 등)의 날짜·설명이 섞였다.
- 왜 검출 모델이 상자 하나로 묶었는지는 모델 내부 판단이라 확인하지 못했다.

### 4.3 DETR p13: 머리글 칸 수와 위치 (사실, 일부 미확인)

- 원본 Table 4의 머리글은 10칸이다(class, ℓ1, GIoU, AP, Δ, AP50, Δ, APS, APM, APL).
- 구조 모델은 머리글 칸을 9개로 예측했고, 본문 3행은 10칸이다.
- 예측한 머리글 칸 상자는 실제 열 위치와 어긋난다. 예: 두 번째 칸은 x=162~247이고, 이 범위에 ℓ1과 GIoU가 함께 들어간다.
  그래서 "GIoU ℓ1"이 한 칸에 들어가고 그다음 칸은 비었으며, "AP"와 "Δ"도 한 칸에 합쳐졌다.
- 본문 2행의 첫 체크 표시(✓)는 OCR에서 "J"로 인식됐다.
- 미확인: 구조 모델이 머리글을 9칸으로 예측한 내부 이유.
- 추론: 이 표에는 세로 괘선이 거의 없고 ℓ1·GIoU 열이 좁게 붙어 있다. 경계가 약한 머리글에서 칸을 하나 적게 낸 것으로 보지만 검증하지 않았다.

## 5. VL 실행 중단(SIGTERM)

- 사실:
  - 파싱 프로세스는 2026-11-11 00:18:35 UTC에 SIGTERM을 받았다. Paddle 로그에 남은 보낸 PID는 0이다. 컨테이너 안의 다른 프로세스가 보냈다면 그 PID가 남으므로, 커널이나 컨테이너 밖에서 온 신호다.
  - 같은 00:18:35~36에 관계없는 다른 프로그램(orca 에이전트 등)도 홈 폴더에 종료 상태 파일을 썼다. 그다음 파일 활동은 00:34:42다.
    컨테이너 전체가 이때 종료됐다.
  - Coder 빌드 기록에는 00:18 무렵 빌드가 없다.
    - 00:33:52 정지(빌드 #8): Terraform이 Docker 컨테이너를 `Drift detected (delete)`로 보고했다. Coder가 정지하기 전에 컨테이너가 이미 없었다.
    - 00:33:54 시작(빌드 #9): 새 컨테이너 `e5ba6637…`를 만들었다.
    - 02:07:52 정지(빌드 #10)와 02:07:54 시작(빌드 #11): 새 컨테이너 `e6eba66b…`를 만들었다. #11은 VS Code 연결로 시작됐다.
  - 워크스페이스에는 자동 정지(TTL)와 자동 시작 일정이 없다(`coder schedule show`).
- 추론: 컨테이너는 Coder 밖, Docker 호스트 쪽 작업으로 종료·삭제됐다.
  정전 뒤 복구 작업이나 호스트 Docker 재시작을 의심하지만, 호스트 로그를 볼 권한이 없어 주체와 이유는 확인하지 못했다.
  Coder 자동 정지는 일정이 없으므로 원인에서 제외했다.

## 6. 시스템 라이브러리가 사라진 이유 (사실)

- 위 빌드 기록처럼 Coder는 워크스페이스를 시작할 때마다 같은 이미지(`workspace-base@sha256:fc0b37e1…`)에서 새 Docker 컨테이너를 만든다.
- 홈 폴더(저장소·`.venv`·모델)는 남지만, `sudo apt-get`으로 설치한 `libgl1`·`libglib2.0-0t64`는 이전 컨테이너의 쓰기 계층에 있었으므로 함께 사라진다.
- 재시작 직후 `ldconfig -p`에서 `libGL.so.1`이 0건이었고, 다시 설치하자 `cv2` 4.10.0을 불러왔다.
