# Structure 표가 구조 토큰 상한에서 잘려 마지막 행에 여러 행이 합쳐짐

- 상태: 부분 해결. 상한에 닿은 표를 규칙 검사로 표시한다. 표 내용은 고치지 않았다.
- 관련 실행: [parsing_structure_20261111T073737685789Z](../../../outputs/parsing_structure_20261111T073737685789Z),
  [chunking_structure_20261111T105933765387Z](../../../outputs/chunking_structure_20261111T105933765387Z)
- 코드: 원인 조사 `8ec2789`(#18), 규칙 검사 0.3.0 `1655543`(#19)
- 출처: `docs/parsing_log/PARSING_ROOT_CAUSES.md`의 1·4.1·8·9.2절(커밋 `1655543`)을 옮겨 다시 구성했다.

## 1. 문제가 어디서 보였나

- 2026-10-30 [정성 검토](2026-10-30_parser-quality-review.md): RAG 논문 6페이지 표에서 SANTA 등 하단 항목이
  독립 행 대신 셀 내용에 남았다. HTML `tr` 수는 VL 72·Structure 62.
- 2026-11-02 규칙 검사 0.1.0: Structure 표 격자 신호 3건 중 하나가 RAG 논문 p6.
- 2026-11-11 재파싱 뒤에도 같았다([병합 해제 재파싱](2026-11-11_vl-merge-off-reparse.md) 5절).

## 2. 원인을 어떻게 찾았나 (사실)

- 원본 표(Table I)의 마지막 부분에는 SANTA부터 G-Retriever까지 11개 행이 따로 있다.
- 출력은 63행이고, 마지막 63번째 행만 칸이 4개다(다른 행은 6개). 이 4칸에 11개 행의 방법명·데이터 출처·형식·단위가
  이어 붙어 있다.
- 표 구조 모델(SLANet_plus·SLANeXt_wired)의 `inference.yml`은 `max_text_length: 500`이다.
- 출력 HTML의 구조 토큰을 모델 사전 기준으로 다시 세면 501개로, 상한과 같은 수준이다.
  모델 사전은 병합 없는 셀을 `<td></td>` 한 토큰으로 묶는다(`merge_no_span_structure: true`).
- 디코더는 정해진 길이만큼만 구조 토큰을 낸다(`table_structure_recognition/processors.py`의 `decode()`).
- 판단(사실): 구조 토큰이 상한에 닿아 63번째 행의 4번째 칸 뒤에서 잘렸다. 그 아래 행의 OCR 글자가 남은
  마지막 칸들에 배정됐다.

원인 조사 4.1절은 같은 실행의 다른 표를 47~197개로 적었고 9.2절은 16~197개로 적었다. 2026-11-12에 저장소의
`structure_token_count()`로 두 Structure 실행의 표 12개를 다시 세면 16·27·36·47·54·67·71·93·130·166·197·501개다.
9.2절 값이 맞고, 4.1절의 47은 다시 셀 때 재현되지 않았다.

## 3. 왜 이 해결책을 골랐나

- 당시 후보(원인 조사 8절): 긴 표를 나눠 인식하거나 구조 토큰 상한에 닿은 표를 표시한다.
  "상한에 닿았는지 규칙 검사로 먼저 표시할 수 있음"이라고 적었다.
- 당시 선택(9.2절, PR #19): 표시만 적용했다. 내용은 고치지 않는다.
- 이번 정리에서 덧붙인 해석(2026-11-12): 나눠 인식하려면 표 영역을 자르고 다시 이어 붙이는 처리가 필요해
  재인식처럼 블록 하나를 다시 넣는 것보다 범위가 크다. 표시는 정답 없이 바로 적용할 수 있고, 다음 단계가
  "이 표의 행 대응은 믿을 수 없다"는 것을 알 수 있게 한다.
- VL 표는 대상에서 뺐다. VL 표는 VLM이 직접 만들어 이 상한과 관계없다.

## 4. 결과

- 규칙 검사 0.3.0에 `table_structure_limit`을 추가했다. Structure 표 12개 중 RAG 논문 p6(501개)에서만 신호가 났다.
- 청킹에서 이 표가 나뉜 청크 6개에 신호가 붙었다. 청크 텍스트와 ID는 이전과 같다
  ([재파싱·재인식 입력 청킹](../../chunking/log/2026-11-11_reparse-rerecognition-input.md)).
- 마지막 행에 합쳐진 11행은 그대로다.

## 5. 남은 문제와 다음 단계

- 표 내용은 여전히 틀린 채로 청크에 들어간다. 긴 표를 나눠 인식하는 방법은 미적용이다.
- 상한 500의 근거는 설치된 모델 설정 파일이다. 다른 모델 버전에서는 값이 다를 수 있다.
