## 3. 표 구조 인식

### 3.1 구조 토큰 상한에서 잘려 마지막 행에 여러 행이 합쳐짐

상태: 부분 해결. 상한에 닿은 표를 규칙 검사로 표시한다. 표 내용은 고치지 않았다.

**1. 어디서 보였나.** [이전 묶음 4절](2026-10-30_structure.md#4-표-인식): RAG 논문 6페이지 표에서 SANTA 등 하단 항목이
독립 행 대신 셀 내용에 남았다. HTML `tr` 수는 VL 72·Structure 62. 규칙 검사 표 격자 신호가 이 묶음에서도 남았다.

**2. 원인을 어떻게 찾았나 (사실).**
- 원본 표(Table I)의 마지막 부분에는 SANTA부터 G-Retriever까지 11개 행이 따로 있다.
- 출력은 63행이고, 마지막 63번째 행만 칸이 4개다(다른 행은 6개). 이 4칸에 11개 행의 방법명·데이터 출처·형식·단위가 이어 붙어 있다.
- 표 구조 모델(SLANet_plus·SLANeXt_wired)의 `inference.yml`은 `max_text_length: 500`이다.
- 출력 HTML의 구조 토큰을 모델 사전 기준으로 다시 세면 501개로, 상한과 같은 수준이다.
  모델 사전은 병합 없는 셀을 `<td></td>` 한 토큰으로 묶는다(`merge_no_span_structure: true`).
- 디코더는 정해진 길이만큼만 구조 토큰을 낸다(`table_structure_recognition/processors.py`의 `decode()`).
- 판단: 구조 토큰이 상한에 닿아 63번째 행의 4번째 칸 뒤에서 잘렸다. 그 아래 행의 OCR 글자가 남은 마지막 칸들에 배정됐다.

원인 조사 4.1절은 같은 실행의 다른 표를 47~197개로 적었고 9.2절은 16~197개로 적었다. 2026-11-12 재계산: 저장소의
`structure_token_count()`로 두 Structure 실행의 표 12개를 다시 세면 16·27·36·47·54·67·71·93·130·166·197·501개다.
9.2절 값이 맞고, 4.1절의 47은 다시 셀 때 재현되지 않았다.

**3. 왜 이 해결책을 골랐나.**
- 당시 후보(원인 조사 8절): 긴 표를 나눠 인식하거나 구조 토큰 상한에 닿은 표를 표시한다.
  "상한에 닿았는지 규칙 검사로 먼저 표시할 수 있음"이라고 적었다.
- 당시 선택(9.2절, PR #19): 표시만 적용했다. 내용은 고치지 않는다. VL 표는 VLM이 직접 만들어 이 상한과 관계없으므로 대상에서 뺐다.
- 이번 정리에서 덧붙인 해석(2026-11-12): 나눠 인식하려면 표 영역을 자르고 다시 이어 붙이는 처리가 필요해 범위가 크다.
  표시는 정답 없이 바로 적용할 수 있고, 다음 단계가 "이 표의 행 대응은 믿을 수 없다"는 것을 알 수 있게 한다.

**4. 결과.**
- 규칙 검사 0.3.0에 `table_structure_limit`을 추가했다. Structure 표 12개 중 RAG 논문 p6(501개)에서만 신호가 났다.
- 청킹에서 이 표가 나뉜 청크 6개에 신호가 붙었다. 청크 텍스트와 ID는 이전과 같다
  ([재파싱·재인식 입력 청킹](../../chunking/log/2026-11-11_reparse-rerecognition-input.md)).
- 마지막 행에 합쳐진 11행은 그대로다.

**5. 남은 문제.** 표 내용은 틀린 채로 청크에 들어간다. 상한 500의 근거는 설치된 모델 설정 파일이며, 다른 모델 버전에서는 다를 수 있다.

### 3.2 머리글 칸 수가 원본보다 하나 적음

상태: 미해결.

**1. 어디서 보였나.** [이전 묶음 4절](2026-10-30_structure.md#4-표-인식): DETR 13페이지 Table 4의 헤더가 합쳐지고 일부 체크 표시를 `J`로 읽었다.
규칙 검사 표 격자 신호 3건 중 하나가 DETR p13이고, 이 묶음에서도 남았다.

**2. 원인을 어떻게 찾았나.**
- 사실: 원본 Table 4의 머리글은 10칸이다(class, ℓ1, GIoU, AP, Δ, AP50, Δ, APS, APM, APL).
  구조 모델은 머리글 칸을 9개로 예측했고, 본문 3행은 10칸이다.
- 사실: 예측한 머리글 칸 상자가 실제 열 위치와 어긋난다. 예: 두 번째 칸은 x=162~247이고 이 범위에 ℓ1과 GIoU가 함께 들어간다.
  그래서 "GIoU ℓ1"이 한 칸에 들어가고 다음 칸은 비었으며, "AP"와 "Δ"도 한 칸에 합쳐졌다.
- 사실: 본문 2행의 첫 체크 표시(✓)는 OCR에서 "J"로 인식됐다.
- 미확인: 구조 모델이 머리글을 9칸으로 예측한 내부 이유.
- 추론: 이 표에는 세로 괘선이 거의 없고 ℓ1·GIoU 열이 좁게 붙어 있다. 경계가 약한 머리글에서 칸을 하나 적게 낸 것으로 보지만 검증하지 않았다.

**3. 왜 이 해결책을 골랐나.** 미적용. 원인 조사에 대응 후보를 적지 않았다.

**4. 결과.** 미적용. 청킹에서는 표 격자 신호가 붙은 채 청크가 된다.

**5. 남은 문제.** 입력을 바꾼 실험(해상도, 표 영역 crop)을 하지 않았다. 같은 페이지에서 VL은 Table 4를 더 잘 유지했다(이전 묶음).

## 4. 차트 인식: 연표 그림을 표로 바꾸며 값을 지어냄

상태: 미해결. 청크에 신호만 붙는다.

**1. 어디서 보였나.** [이전 묶음 8절](2026-10-30_structure.md#8-문서별-관찰): 슬라이드 `0e94…` 6페이지 우주개발 도표의 비정상 수치표.
규칙 검사 긴 번호 나열 1건(슬라이드 p6)이 이 묶음에서도 남았다. 같은 그림을 VL은 생성 한도까지 반복했다
([VL 기록 4절](2026-11-11_vl.md#4-vlm-영역-인식-생성-한도까지-반복된-출력)).

**2. 원인을 어떻게 찾았나.**
- 사실: Structure는 연표 그림을 `chart`로 검출하고 PP-Chart2Table로 표를 만들었다. 출력은 63행 "ID | Name | Year | Value"다.
- 사실: 5행부터 이름이 "Lunar Vinyus"로 반복되고, 연도는 58에서 121까지 1씩 증가한다.
  그림의 연도축은 58~76이고 "Lunar Vinyus"라는 항목은 없다. 77~121년과 이 이름은 원본에 없는 값이다.
- 사실: 출력은 PP-Chart2Table의 `tokenizer.json`으로 962토큰이다. 이 모델의 기본 생성 한도
  (`GOT_ocr_2_0.py`의 `PPChart2TableInference`, 1,024)에 닿지 않았다. 기준 실행과 새 실행의 출력이 같다.
- 추론: VL과 같은 "한도에서 잘림"은 아니다. 데이터 표가 없는 그림을 차트→표 모델에 넣어 표 형식에 맞춰 값을 지어낸 결과로 본다.

**3. 왜 이 해결책을 골랐나.** 미적용. 당시 후보(원인 조사 8절)는 축 범위 밖 값·반복 이름 검출이며,
정답 없이 쓸 수 있는 규칙인지 확인이 필요하다고 적었다. 청킹은 원문일 가능성을 규칙으로 가를 수 없어 지우지 않고 신호만 붙인다.

**4. 결과.** 미적용. 청킹에서 이 차트는 `long_number_sequence` 신호가 붙은 청크 4개가 됐다.

**5. 남은 문제.** PP-Chart2Table이 63행에서 멈춘 이유는 실험하지 않았다. 데이터 차트가 아닌 그림을 차트 인식에서 빼는
방법과 축 범위 밖 값 검출 규칙을 비교해야 한다.
