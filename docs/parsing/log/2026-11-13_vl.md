## 1. 실행 개요

### 1.1 목적

"관찰만"이거나 원인이 미확인이던 VL 이슈의 원인을 찾고, 우리 코드로 고칠 수 있는지와 고치는 방법을 정한다.
수정은 이 묶음에서 하지 않았다.

### 1.2 조건

| 항목 | 값 |
|---|---|
| 모델 | 캐시된 PaddleOCR-VL-1.6(0.9B), 레이아웃 PP-DocLayoutV3. 다운로드 없음 |
| 실험 단위 | 블록 하나를 잘라 VLM에 넣음. 페이지 전체 재파싱은 하지 않음 |
| 실행 환경 | Linux 컨테이너, CPU 8스레드, 한 번에 실험 하나 |
| 기본 입력 | 파이프라인과 같은 BGR 배열, 파이프라인이 고르는 프롬프트 |
| 바꾼 변수 | 실험마다 하나: 렌더링 DPI, 색 순서(BGR·RGB), 프롬프트, 자른 범위 |
| 비교 근거 | PDF 텍스트층 단어(좌표 포함), 원본 그림의 실제 해상도 |

재현 확인(사실): 블록만 다시 인식하고 파이프라인과 같은 후처리를 거친 출력이 저장된 값과 글자 단위로 같았다
(DETR 표, 3M p9 표, RAG 그림, NUS 그림, 3M p15 표, 슬라이드 p15 차트, 재인식 기록의 Toyota p7).
그래서 아래 실험은 "한 번에 변수 하나만 바꾼 비교"로 본다.

### 1.3 공통 사실

- 생성은 결정적이다. 첫 실행(Windows)과 재파싱(Linux)에서 bbox·라벨이 같은 블록 398개의 출력이 같았다.
  출력이 다른 22개는 모두 text 라벨이며, 첫 실행에서 영역 병합을 켠 영향으로 본다(추론).
- 로컬 실행 경로는 `temperature`·`top_p`·`repetition_penalty`를 경고만 내고 버린다
  (`paddlex/inference/models/doc_vlm/predictor.py:233-244`). 디코딩 설정으로는 출력을 바꿀 수 없다.
- 모델 입력 크기는 `smart_resize`가 최대 1,003,520픽셀로 줄인다(`paddlex/inference/models/doc_vlm/processors/paddleocr_vl/_siglip.py:59-110`).
  렌더링 DPI를 올려도 모델이 실제로 보는 해상도는 이 상한에 묶인다.

## 2. 입력·렌더링: VLM 입력 색 순서

상태: 미해결. 경로를 확인했고, 품질 영향은 방향이 일정하지 않아 적용하지 않았다.

**1. 어디서 보였나.** [이전 묶음 2절](2026-11-11_vl.md#2-입력렌더링-vlm이-빨강파랑이-바뀐-이미지를-받음): VLM이 빨강·파랑이 바뀐 이미지를 받는 경로를 확인했지만
의도된 동작인지와 품질 영향을 확인하지 않았다.

**2. 원인을 어떻게 찾았나.**
- 사실(경로):
  1. 프로젝트가 RGB를 BGR로 뒤집어 넘긴다(`parsing/pdf_parser.py`의 렌더링 함수).
  2. 파이프라인의 `ReadImage(format="BGR")`(`paddlex/inference/pipelines/paddleocr_vl/pipeline.py:159`)는 배열을 그대로 반환한다
     (`paddlex/inference/common/reader/image_reader.py:51-55`).
  3. 블록을 잘라 변환 없이 VLM 입력 목록에 넣는다(`pipeline.py:301-353`, `515-526`).
  4. 로컬 처리기 `fetch_image`는 `Image.fromarray(image)` 뒤 `.convert("RGB")`만 한다. 채널 순서는 바꾸지 않는다
     (`paddlex/inference/models/doc_vlm/processors/common.py:447-448`, `464`).
- 사실(같은 라이브러리의 다른 경로): 서버 경로는 같은 배열을 `cv2.cvtColor(BGR2RGB)`로 바꿔 보낸다(`doc_vlm/predictor.py:485`).
  파이프라인도 저장용 그림 crop은 RGB로 바꾼다(`pipeline.py:625`). 모델 카드 예제는 `Image.open(...).convert("RGB")`를 쓴다.
- 추론: 로컬 경로에서만 색이 뒤집히는 PaddleX 내부 불일치로 본다. 파일 경로로 입력해도 cv2가 BGR로 읽으므로 같은 문제가 생긴다.
- 사실(영향, 블록 단위 실험, 바꾼 변수는 색 순서 하나):

  | 블록·조건 | BGR(현재) | RGB |
  |---|---|---|
  | Toyota p2, 576 DPI | 텍스트층 재현율 0.79 | 0.89 |
  | NUS p9 그림, 144 DPI | 두 묶음 누락 | `Minor (non-BIZ) - Economics` 복구, 한 묶음은 여전히 누락 |
  | 슬라이드 p6, `OCR:` 프롬프트, 576 DPI | 163토큰에서 정상 종료 | 숫자 이어 세기로 한도 도달 |
  | 슬라이드 p15 차트, 144 DPI | 12개국×12년 표 | 전혀 다른 표(연도×3열, 깨진 머리글) |
  | RAG p3 그림, 144 DPI | `原始` | `原始`(같음) |
  | Toyota p7 | 106토큰 | 103토큰, 단어 2개 차이 |

- 사실: 색 영향을 받는 픽셀 비율(R과 B 차이가 16 초과)은 Toyota p7 0%, Toyota p2 4.7%, 슬라이드 p6 11.0%다.
- 추론: 이 표본에서 색 순서는 품질을 한 방향으로 바꾸기보다 결정적 생성의 결과를 흔드는 요인으로 작용한다.

**3. 왜 이 해결책을 골랐나.** 미적용. 후보는 다음과 같다.

| 후보 | 판단 |
|---|---|
| VL 어댑터에서 인식 모델 입력만 RGB로 바꿈 | 공식 예제·서버 경로와 맞는다. 다만 PaddleX 내부 속성에 기대므로 버전 고정과 시작 시 검사가 필요하다(속성 경로 미확인) |
| PaddleX에 이슈 보고 | 근본 해결이지만 우리가 통제할 수 없다 |
| 재인식만 RGB로 | 이미 `channel_order` 설정으로 바꿀 수 있다 |

출력이 블록마다 다른 방향으로 바뀌므로, 같은 27페이지 전체에서 블록 단위 차이·규칙 신호·텍스트층 재현율을 비교한 뒤 적용한다.

**4. 결과.** 미적용.

**5. 남은 문제.** 27페이지 전후 비교. `run.json`에 VLM 입력 색 순서를 기록하는 필드가 없다.

## 4. VLM 영역 인식

### 4.1 3M p9 Elected를 Executed로 읽음

상태: 미해결(P-06). 원인을 확인했고 대응은 미적용이다.

**1. 어디서 보였나.** [첫 묶음 4.2절](2026-10-30_vl.md#42-관찰만-한-인식-문제): 3M p9 표 머리글 `Year Elected to Present Position`을 `Executed`로 읽었다.
두 실행 모두 같다. 같은 머리글이 있는 3M p8 표는 두 실행 모두 `Elected`로 맞게 읽었다.

**2. 원인을 어떻게 찾았나.**
- 사실: 레이아웃 표 상자의 윗변이 y=114px(57.0pt)다(PP-DocLayoutV3 점수 0.946, 좌표 `[111,114,1093,484]`).
  텍스트층의 `Year`·`Elected`는 y 52.62–59.93pt에 있어 단어 높이의 약 60%가 상자 밖이다(상자와 겹친 비율 0.40).
- 사실: 영역 자르기는 상자 좌표를 그대로 쓴다(`paddlex/inference/components/common/crop_image_regions.py:64-65`).
  상자를 넓히는 `layout_unclip_ratio` 기본값은 `[1.0, 1.0]`이라 넓히지 않는다(PaddleOCR-VL-1.6 파이프라인 설정).
- 실험(바꾼 변수는 상자 윗변 하나, 144 DPI·BGR·같은 프롬프트 고정): 윗변만 14px 넓히자 `Elected`로 읽었다.
  원시 OTSL 1,335자 중 바뀐 곳은 이 단어 하나였다.
- 추론: 아랫부분만 남은 글자를 언어 모델이 그럴듯한 다른 단어로 채웠다.

**3. 왜 이 해결책을 골랐나.** 미적용. 후보는 다음과 같다.

| 후보 | 판단 |
|---|---|
| 규칙 검사에 "잘린 텍스트층 단어" 신호 추가 | 텍스트층 단어가 어느 블록과 10~70%만 겹치고 어느 블록에도 70% 이상 들지 않으면 표시한다. 재파싱 실행 12,417단어 중 9개가 걸렸고 3M p9 두 단어가 포함됐다. 나머지는 Toyota p32·p34와 뉴스 p1이다 |
| 신호가 붙은 블록만 상자를 넓혀 재인식 | 원인을 직접 고친다. 넓히는 폭은 설정값으로 둔다. 지금 재인식은 표를 대상에서 빼므로 표 입력 처리를 재현할지 먼저 정해야 한다 |
| 전체 `layout_unclip_ratio` 확대 | 비율 방식이라 높이 370px 표에서 9px를 넓히려면 1.05 이상이 필요하고, 모든 블록 사이의 겹침이 늘어난다(측정하지 않음). 권하지 않는다 |

신호와 대상 재인식을 함께 쓰는 안을 고른다. 겹침 비율은 이 표본에서 정한 값이라 설정으로 둔다.

**4. 결과.** 미적용. 실험에서 윗변을 넓히면 고쳐지는 것을 확인했다.

**5. 남은 문제.** 신호 9개 전체의 재인식 전후 비교(텍스트층 재현율, 새 중복). 표 재인식 방식.

## 5. 표·차트·수식 인식

### 5.1 표 열·머리글 손상

상태: 미해결(P-10). 원인은 모델 출력 자체이고, 빈 열 정리와 누락 탐지만 가능하다.

**1. 어디서 보였나.** [첫 묶음 5절](2026-10-30_vl.md#5-표-인식-열헤더-손상). 두 실행 모두 같다.
- DETR p13 Table 3(블록 6): 6열로 나왔고 마지막 Δ열(`-6.5, -1.6, -0.9, -1.4, -`)이 없다. 텍스트층과 대조하면 숫자 20개 중 5개가 없다.
- 3M p15(블록 16): 숫자 62개는 모두 있다. 대신 `Year ended`가 colspan 3이고 모든 행 끝에 빈 5번째 열이 있다.

**2. 원인을 어떻게 찾았나.**
- 사실: 모델이 낸 원시 OTSL이 그렇게 생겼다. DETR은 모든 행이 `<fcel>` 6개라 행 길이가 같고, 그래서 `otsl_pad_to_sqr_v2`의
  자르기가 작동하지 않았다(`paddlex/inference/pipelines/paddleocr_vl/uilts.py:894-949`). 3M은 행 끝의 `<ecel>`과 머리글의 `<lcel><lcel>`을 모델이 직접 냈다.
- 실험(바꾼 변수 DPI): DETR을 288 DPI로 다시 인식해도 6열이 유지됐고, 이번에는 Δ열 대신 `learned at …` 텍스트 열이 빠졌다.
- 추론: 2단 머리글을 2칸으로 합쳐 열 수를 먼저 정한 뒤 본문도 그 수만큼 생성했다. 3M의 빈 열은 원본에서 따로 떨어진 `$` 열을 숫자와 합치면서 열 수는 유지한 흔적으로 본다.

**DETR p13 Table 3에서 열 수가 처음에 정해지는 과정.**
원본은 머리글이 두 줄인 7열 표다. 텍스트층 단어의 x좌표로 보면 윗줄 `spatial pos. enc.`(x 77~142)가 아랫줄 `encoder`·`decoder` 두 열을 덮고,
`output pos. enc.`(x 191~256)는 세 번째 열 `decoder` 위에 있다. 숫자 열(AP, ∆, AP50, ∆) 위의 윗줄은 비어 있다.

```text
원본(텍스트층)                                       VL 출력
머리글 1: [spatial pos. enc. ──────] [output pos. enc.]    (없음)
머리글 2:  encoder   decoder          decoder   AP ∆ AP50 ∆   spatial pos. enc. encoder | output pos. enc. decoder | AP | Δ | AP50 | Δ
본문 1:    none      none             learned at input  32.8 -7.8 55.2 -6.5   none | none | learned at input | 32.8 | -7.8 | 55.2
```

1. 사실: VL은 머리글 두 줄을 한 줄로 합쳤다. 출력 첫 두 칸은 윗줄 글자에 아랫줄 글자를 이어 붙인 모양(`spatial pos. enc.` + `encoder`,
   `output pos. enc.` + `decoder`)이다. 윗줄 글자가 두 개라 두 칸만 만들었고 그 사이의 spatial 쪽 `decoder` 열이 빠져 머리글이 6칸이 됐다.
2. 사실: 본문 행은 원래 값 7개를 가진다. 출력은 앞에서부터 6개만 쓰고 줄을 끝냈다. 앞 세 칸(설정 이름)은 모두 남고 마지막 ∆열이 통째로 빠졌다.
   그래서 머리글과 값이 한 칸씩 어긋난다. `AP` 아래에 `learned at input`이, `Δ` 아래에 AP 값 `32.8`이 온다.
3. 사실: PaddleOCR-VL은 표를 OTSL 토큰 열로 왼쪽 위부터 하나씩 생성하고, 이미 낸 토큰은 고치지 않는다. 원시 출력의 모든 행이 `<fcel>` 6개라
   후처리 `otsl_pad_to_sqr_v2`는 아무것도 바꾸지 않았다. 6열은 후처리가 아니라 모델 출력 그대로다.
4. 추론: OTSL은 표를 직사각형 격자로 나타내므로 학습 데이터의 모든 줄은 칸 수가 같다. 모델은 첫 줄(머리글)에서 정한 칸 수를 뒤 줄에서도 따르도록
   학습됐다고 본다. 이 표는 첫 줄을 쓰는 단계에서 칸 하나를 잃었고, 본문 줄은 그 틀에 맞춰 마지막 값을 버렸다.
5. 추론: 올바르게 쓰려면 첫 줄을 `<fcel>spatial pos. enc.<lcel><fcel>output pos. enc.<ecel><ecel><ecel><ecel><nl>`처럼 병합 칸과 빈칸을 표시한 7칸으로 내야 한다.
   모델은 두 줄을 접는 쪽을 택했다. 출력 모양에서 짐작한 것이고 모델 내부에서 확인하지 않았다.
6. 사실: 288 DPI에서도 6열이었고 이번에는 Δ열 대신 `learned at …` 열이 빠졌다. 추론: 글자가 안 보여서가 아니라 머리글 구조를 해석하는 단계의 문제라
   해상도로는 고쳐지지 않는다.

**표 점수(DETR p13 Table 3).** 텍스트층 단어를 줄(y 중심 차 3pt 이하)과 칸(단어 간격 6pt 미만)으로 묶어 기준 격자를 만들고,
칸이 가장 많은 줄들로 7개 열의 x 범위를 정했다. 머리글 줄의 글자는 x 범위가 겹치는 열에 모두 붙여 열마다 머리글 경로를 만들었다.
출력 HTML은 rowspan·colspan을 펼친 뒤, 숫자가 처음 나오는 줄 앞을 머리글로 봤다. `\Delta`와 `∆`, `AP_{50}`과 `AP50`처럼 표기만 다른 것은 같게 보고,
모양이 비슷한 다른 글자(한자 `一`)는 다르게 봤다. 기준 격자는 사람이 적은 정답이 아니라 텍스트층에서 만든 것이다.

| 지표 | 뜻 | VL | Structure |
|---|---|---|---|
| 열 수 | 기준 7열 | 6 | 7 |
| 머리글 경로 일치 | 열마다 머리글이 기준과 같은가 | 1/7 | 7/7 |
| 본문 칸 일치 | 같은 (행, 열) 위치의 값이 같은가 | 30/35 | 33/35 |
| 머리글까지 맞은 본문 칸 | 값과 그 열의 머리글이 모두 맞은 칸 | **5/35** | **33/35** |
| 숫자 회수율 | 텍스트층 숫자 다중집합 중 출력에 있는 것 | 14/18 | 18/18 |
| 추가 숫자 | 텍스트층에 없는 숫자 | 0 | 0 |

- VL의 본문 칸 일치는 30/35로 높아 보이지만, 머리글이 어긋나 값을 바른 의미로 읽을 수 있는 칸은 5/35(첫 열)뿐이다.
  빠진 5칸은 마지막 ∆열(숫자 4개와 `-` 1개)이다. 첫 기록의 "숫자 20개 중 5개"는 `-`까지 센 값이고, 이번 집계는 숫자만 세어 18개 중 4개다.
- Structure가 틀린 2칸은 마지막 행이다. `-`를 한자 `一`로 읽었고, 마지막 ∆의 `-`는 빈칸이 됐다. 다단 머리글(colspan 2, rowspan 2)은 맞았다.
  다만 `<th>`가 없어 청킹이 머리글 둘째 줄을 데이터 행으로 읽는 문제(C-12)는 남는다.
- 조건: PDF `2005.12872v3.pdf` 13쪽, 기준 bbox는 VL 블록 6의 PDF 좌표 `[33.5, 329.5, 378.5, 416.0]`. 두 실행에서 이 bbox와 가장 많이 겹치는 표 블록
  (VL `…:p13:vl:6`, Structure `…:p13:structure:5`)을 비교했다. 재현 스크립트 미보관, 실험 조건만 기록.
- 하이브리드 파싱에 주는 근거: 텍스트층으로 만든 열 수(7)와 맞는 쪽의 구조를 고르면 이 표는 Structure를 쓰고, VL은 숫자 대조로 누락을 표시한다.

**3. 왜 이 해결책을 골랐나.** 미적용. 후보는 다음과 같다.

| 후보 | 판단 |
|---|---|
| 빈 열 제거 정규화(파생 필드) | 모든 칸이 비었거나 colspan 연장인 열만 지운다. 3M p15에 시험하자 20×5가 4열이 되고 `Year ended`가 2018·2017 두 열에 걸렸다. 값이 빠진 DETR은 복구하지 못한다 |
| 텍스트층 숫자 대조 신호 | 표의 숫자와 텍스트층 숫자를 다중집합으로 비교해 누락·추가를 기록한다. DETR 누락 5칸(숫자 4개, `-` 1개)을 잡았다 |
| 텍스트층 열 수 대조 신호 | 위 표 점수처럼 텍스트층 단어의 x 범위로 열 수를 세어 출력 열 수와 비교한다. DETR은 7 대 6으로 잡힌다. 머리글 어긋남(5/35)은 숫자 대조로는 보이지 않아 이 신호가 따로 필요하다 |
| 누락이 확인된 표는 수치 검색에서 보류 | 이미지와 캡션은 보존한다 |
| PyMuPDF `find_tables(strategy="text")`로 대체 | 시험 결과 단어를 잘게 쪼개 그대로 쓸 수 없었다 |

**4. 결과.** 미적용.

**5. 남은 문제.** 텍스트층이 없는 표의 누락 탐지.

### 5.2 슬라이드 p15 그래프 수치표

상태: 미해결(P-15). 모델 한계이며 탐지·우회만 가능하다.

**1. 어디서 보였나.** [첫 묶음 4.2절](2026-10-30_vl.md#42-관찰만-한-인식-문제): 생성 수치표가 원본 막대 변동과 맞지 않았다. 두 실행 모두 같은 12개국×12년 표다.

**2. 원인을 어떻게 찾았나.**
- 사실: `use_chart_recognition=True`이면 chart 블록을 같은 PaddleOCR-VL에 `"Chart Recognition:"` 프롬프트로 넣는다
  (`paddlex/inference/pipelines/paddleocr_vl/pipeline.py:321-326`). 별도 차트 모델이 아니다. 공식 기본값은 꺼짐이고 프로젝트가 켰다.
- 사실: 원본은 값 라벨이 없는 3D 막대그래프 래스터(569×598px)다. 144 DPI 렌더링이 원본보다 크고 텍스트층도 없다. 정확한 값이 픽셀에 없다.
- 사실: 출력 값이 모두 10만 단위다. Ecuador를 뺀 9개국은 연간 증가가 정확히 100,000이고 Kamerun은 50,000이다.
- 실험: 재인식에서도 같은 출력이 재현됐다(240.4초). RGB로 넣자 연도×3열 구조에 `Exports Vol Balalan in Tohien` 같은 깨진 머리글이 붙은
  전혀 다른 표가 나왔고, 값은 역시 등차수열이었다.
- 추론: 그래프를 읽은 값이 아니라 생성한 값이다. 해상도를 올려도 고쳐지지 않는다.

**3. 왜 이 해결책을 골랐나.** 미적용. 후보는 다음과 같다.

| 후보 | 판단 |
|---|---|
| chart 출력을 수치 검색에서 빼고 `generated_estimate`로 표시 | 그림·캡션 연결은 유지한다 |
| 행별 등차수열·지나친 반올림 신호 | 정답 없이 적용할 수 있다. 정상 차트의 오탐 수를 먼저 잰다 |
| 차트 인식 끄기 | 그 블록에 무엇이 나오는지 확인하지 않았다 |
| PP-Chart2Table과 비교 | 시험하지 않았다 |

**4. 결과.** 미적용.

**5. 남은 문제.** 값을 복원할 근거가 원본에 없다. 이런 페이지는 이미지 검색 채널이 맡는다.

### 5.3 DETR p5 식 (2)의 첨자

상태: 정상 동작(P-17). 파싱 오류가 아니다.

**1. 어디서 보였나.** [첫 묶음 8절](2026-10-30_vl.md#8-두-파서에서-공통으로-관찰된-인식-문제-vl-쪽-근거): 두 파서 모두
식 (2)를 `\hat{b}_{\hat{\sigma}}(i)`로 출력했고, 당시에는 `\hat{b}_{\hat{\sigma}(i)}`가 맞다고 보았다.
같은 식의 `\hat{p}_{\hat{\sigma}(i)}`는 두 파서 모두 첨자 안에 `(i)`를 넣었다.

**2. 원인을 어떻게 찾았나.**
- 사실: `source.pdf` 5페이지의 글자 정보를 읽었다. p̂ 뒤의 `σ̂ ( i )`는 모두 CMR7/CMMI7 6.97pt로 아래첨자 크기다.
  b̂ 뒤에는 `σ̂`만 CMMI7 6.97pt이고 `( i )`는 CMR10/CMMI10 9.96pt 본문 크기에 기준선 위치다.
- 사실: 600 DPI로 렌더링해도 b̂_σ̂ 뒤의 `(i)`가 본문 크기로 보인다.
- 판단: 두 모델은 인쇄된 모양을 그대로 옮겼다. 당시 정답으로 둔 형태는 원문 조판이 아니라 의미상 의도였다. 저자 원고의 오타로 보이지만 추론이다.

**3. 왜 이 해결책을 골랐나.** 대응하지 않는다. 출력을 의미에 맞게 고치면 원문과 다른 값을 만들게 된다.

**4. 결과.** 상태를 "정상 동작"으로 바꿨다.

**5. 남은 문제.** 없음.

## 6. 결과 변환·저장: bbox 경계 초과와 partial

상태: 미해결(P-19). 원인을 확인했고 대응은 미적용이다.

**1. 어디서 보였나.** [첫 묶음 1.3절](2026-10-30_vl.md#13-구조무결성-검사-결과): Toyota p21이 `partial`이다. 두 VL 실행 모두 같다.
문제 블록은 내용이 빈 저점수(0.308) vision_footnote이고, `bbox_image_pixels=[814,888,1684,901]`이 `bbox_pdf_points` x1=842.0이 된다.
페이지 폭은 841.89pt라 0.10999pt 넘는다. Structure는 경계에 닿은 상자가 없어 `ok`다.

**2. 원인을 어떻게 찾았나.**
- 사실: PyMuPDF가 렌더링 크기를 바깥쪽으로 올림한다. 페이지 841.89×595.276pt × 2 = 1683.78×1190.55px인데 실제 이미지는 1684×1191px다.
- 사실: 좌표 변환 행렬은 정확한 배율 0.5를 쓴다. 그래서 이미지 오른쪽 끝 x=1684는 842.0pt가 된다. 모델 상자는 이미지 안에 있고(x1이 폭과 같음),
  규칙 검사의 픽셀 경계 검사도 통과한다. CropBox와 MediaBox가 같고 회전이 없어 그 문제가 아니다.
- 사실: 초과량은 (1684−1683.78)/2 = 0.11pt로 렌더링 1px(0.5pt)보다 항상 작다. 같은 올림 차이가 Toyota(가로 0.22px),
  DETR(0.284px), NUS(0.874px, 최대 0.437pt)에 있다.
- 사실(상태가 바뀌는 경로): 검토 PDF의 경계 검사(`parsing/review_pdf.py`)에 허용 오차가 없어 warning이 되고,
  `parsing/run.py`가 review warning을 페이지 상태 `partial`로 올린다.

**3. 왜 이 해결책을 골랐나.** 미적용. 후보는 다음과 같다.

| 후보 | 판단 |
|---|---|
| 검토 PDF 경계 검사의 허용 오차를 렌더링 1픽셀의 PDF 크기로 | 행렬에서 계산해 넘기므로 고정값이 아니다. 허용 오차 이하면 초과량만 기록하고 warning으로 바꾸지 않는다 |
| 행렬 수정 | 마지막 픽셀 열이 실제로 페이지 밖까지 걸쳐 있어 행렬은 맞다. 고치지 않는다 |
| `bbox_pdf_points` 자르기 | 원래 값은 보존한다. 필요하면 잘린 좌표와 초과량을 파생 필드로 둔다 |

review warning을 처리 상태(`partial`)에 반영할지는 따로 정해야 한다. 지금은 품질 신호와 처리 상태가 섞여 있다.

**4. 결과.** 미적용.

**5. 남은 문제.** 허용 오차 경계 테스트(폭 841.89, 144 DPI, x1이 이미지 폭과 같은 블록과 2px 넘는 블록, 회전 페이지).

## 7. 후처리: 재인식

### 7.1 생성 한도 반복이 576 DPI로 남은 이유

상태: 부분 해결(P-04, C-02). Toyota p2만 해결됐다.

**1. 어디서 보였나.** [이전 묶음 4.5절](2026-11-11_vl.md#45-남은-문제): 슬라이드 p6은 576 DPI에서도 4,096토큰까지 반복했고(1,832초),
Toyota p7은 106토큰에서 끝났지만 일부만 옮겼다.

**2. 원인을 어떻게 찾았나.**
- 사실(모델이 본 해상도): 재인식 기록의 `input_size`는 줄이기 전 crop 크기다. 같은 `smart_resize`로 다시 계산하면 다음과 같다.

  | 블록 | 기록된 크기 | 모델 입력 | 실효 DPI | 비고 |
  |---|---|---|---|---|
  | 슬라이드 p6 | 3844×2112 | 1344×728 | 201.4 | 144 DPI 때(952×532, 142.7)보다 가로세로 1.41배뿐. 상한에서 가능한 최대는 202.5 |
  | Toyota p7 | 2260×1800 | 1120×868 | 285.5 | |
  | Toyota p2 | 1060×776 | 1064×784 | 578 | 줄어들지 않음 |

- 사실(원본 해상도): 슬라이드 p6 차트는 PDF 안의 JPEG(xref 47, 1350×1080px)로 204.2 DPI다. Toyota p7 원뿔 두 개는 xref 63(316×529)과
  xref 73(319×487)으로 둘 다 약 150 DPI다. 그 이상으로 렌더링해도 정보가 늘지 않는다.
- 실험(슬라이드 p6, 576 DPI 같은 픽셀 고정, 바꾼 변수는 프롬프트·색 순서·반복 벌점):
  - `Chart Recognition:` 프롬프트는 BGR, RGB, BGR에 반복 벌점 1.05 모두 `Lunar Orbit | 58.5, 59.5 … 131.5`처럼 연도 눈금(58~76) 밖까지 세며 한도에 닿았다.
  - `OCR:` 프롬프트에 BGR을 넣으면 163토큰에서 스스로 끝났고 축 라벨 30여 개를 정확히 옮겼다(180초). 프로젝트 채택 규칙을 적용하면 채택된다.
  - `OCR:` 프롬프트에 RGB를 넣으면 `58, 60…76` 뒤에 `1987…2250`을 세며 한도(1,536)에 닿았다.
- 사실(생성 설정): 파이프라인이 생성 한도를 4,096으로 채운다(`paddleocr_vl/pipeline.py:504-505`). 모델 기본값은 8,192다.
  모델 `generate()`는 `max_new_tokens`와 `use_cache`만 넘긴다. 부모 generate를 직접 불러 반복 벌점을 적용하자 값은 바뀌었지만(58.5 → 58.2) 루프는 끊기지 않았다.
- 사실(판정 빈틈): 규칙 검사의 연속 번호는 줄 머리의 `N |`와 `N.` 형식만 센다. 숫자만 있는 줄(1987…2250)과 표 칸 안에서 늘어나는 소수(`| 58.2 |`)는 신호가 없다.
- 추론: 늘어나는 숫자는 매번 다른 토큰이라 반복 벌점이 잘 듣지 않는다. 프롬프트를 바꾸면 증상이 사라질 수 있지만 입력이 조금만 달라도 숫자 이어 세기에 다시 들어간다.
- 추론(C-02): 이 그림은 값 표가 없는 연표인데 레이아웃 모델이 chart로 분류해서 차트 프롬프트가 골라졌다.

**3. 왜 이 해결책을 골랐나.** 미적용. 후보는 다음과 같다.

| 후보 | 판단 |
|---|---|
| 재인식 시도를 (프롬프트, 렌더링 배율) 목록으로 | chart는 `Chart Recognition:` 다음에 `OCR:`로 넘어간다. 라벨별 시도 목록은 설정으로 둔다. `OCR:` 결과는 `content_source`에 프롬프트를 남겨 차트 값이 아니라 라벨 텍스트임을 구분한다 |
| 시도 전에 모델 입력 크기와 원본 래스터 DPI 계산 | 입력이 이전 시도와 같아지거나 원본 DPI의 약 2배를 넘는 시도는 건너뛰고 사유를 남긴다. 슬라이드 p6처럼 같은 입력에 30분을 쓰지 않는다 |
| 반복 판정에 단조 증가 숫자열 추가 | 숫자만 있는 줄과 표 칸의 정수·소수가 대상이다. 기존 27페이지의 오탐 수를 먼저 잰다 |
| 반복 벌점 강제 적용 | 내부 API를 직접 부르고, 이 표본에서 효과가 없었다. 쓰지 않는다 |

세 후보를 함께 쓴다. `OCR:` 대체 시도도 숫자 루프에 빠질 수 있으므로 판정 보강 없이 쓰지 않는다.

**4. 결과.** 미적용.

**5. 남은 문제.** 같은 3블록에 BGR·RGB 각각으로 바뀐 재인식을 실행해 채택률·시간·신호를 비교한다. 차트 값 복원은 이 그림 형식에서 모델 한계로 본다.

### 7.2 Toyota p7 부분 전사

상태: 미해결(C-01). 원인을 확인했고 대응은 미적용이다.

**1. 어디서 보였나.** [청킹 2026-11-11 VL 2절](../../chunking/log/2026-11-11_vl.md#2-입력-재인식-결과-적용): 576 DPI 재인식 출력이 106토큰이다.
영어 라벨과 아래쪽 상자 2개만 옮겼고, 원뿔 안 일본어는 대부분 빠졌다(한중일 문자 23자). `Cone`을 `Core`로 읽었다.

**2. 원인을 어떻게 찾았나.** 바꾼 변수는 자른 범위와 배율이다.

| 실험 | 입력 | 모델 입력 | 픽셀 밀도 | 결과 |
|---|---|---|---|---|
| E1 블록 전체 | 576 DPI | 1120×868 | 3.96 px/pt | 106토큰, 한중일 문자 23자(재인식 기록과 같음) |

- 사실: 색 순서는 원인이 아니다. 이 그림은 R과 B 차이가 16을 넘는 픽셀이 0%다.
- 사실: 원본은 약 150 DPI JPEG이고 일본어 글자 높이는 원본 기준 대략 5~8px다(눈으로 어림한 값). 완전한 전사는 보장할 수 없다.

**3. 왜 이 해결책을 골랐나.** 미적용. 후보는 다음과 같다.

| 후보 | 판단 |
|---|---|
| 큰 image 블록을 겹치는 타일로 나눠 재인식 | 원인을 직접 다룬다. 타일 크기는 원본 래스터 DPI의 약 2배와 최대 픽셀 상한으로 정한다. 고정 격자는 글자 줄을 자를 수 있어, 캐시된 `PP-OCRv6_medium_det`로 글자 줄을 검출해 묶은 영역을 타일로 쓰는 안이 1순위다(미검증). 겹친 부분의 중복 제거 규칙이 필요하다. 타일 하나에 약 30~100초 |
| 부분 전사 신호 | 검출된 글자 줄 수 대비 출력 줄 수, 텍스트층이 있으면 단어 재현율을 쓴다. 채택 기준과 따로 기록한다 |

**4. 결과.** 미적용. 타일 하나에서 회복을 확인했다.

**5. 남은 문제.** 일본어를 사람이 옮긴 소량 정답을 평가 전용으로 만들어 문자 재현율·정밀도를 비교한다. 원본 해상도 한계는 기록으로 남긴다.

## 8. 해석과 한계, 다음 단계

- 블록마다 한두 번 실험한 결과다. 일반화하지 않는다.
- VL의 실수는 생성 단계에서 생긴다. 그럴듯한 다른 단어로 바꾸거나(`Executed`, `原始`), 항목을 빠뜨리거나(NUS p9), 값을 지어낸다(슬라이드 p15).
  원시 결과에 글자를 따로 본 근거(OCR 줄)가 남지 않고 디코딩 설정도 무시되므로, 우리 코드로는 다시 인식하거나 텍스트층과 대조해 탐지하는 것까지만 가능하다.
  Structure는 원시 OCR 줄이 남아 저장된 결과로 상당 부분 되돌릴 수 있다. 두 파서의 고칠 수 있는 것과 없는 것을 나눈 비교와
  하이브리드 파싱이 필요한 이유는 [Structure 기록 8.1절](2026-11-13_structure.md#81-하이브리드-파싱이-필요한-이유)에 있다.
- 텍스트층이 없는 7페이지에서는 VL의 바꾸기·누락을 탐지할 근거가 없다.
- 다음 단계(제안): 설정·검사 신호(P-19, 새 신호들) → 재인식 확장(P-04·C-01·P-06·P-07) 순서로 적용하고, P-05는 27페이지 전후 비교 뒤 정한다.
